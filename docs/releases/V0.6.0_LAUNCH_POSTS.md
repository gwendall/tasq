# Tasq v0.6.0 launch posts

These drafts announce the published open-source public alpha without extending
its support claims. The primary action is to run the isolated demo; the
secondary action is to inspect the [source](https://github.com/gwendall/tasq)
and the immutable
[v0.6.0 release](https://github.com/gwendall/tasq/releases/tag/v0.6.0).

They replace the v0.5.1 drafts, which were never published and which led with
**three sessions of one tool** colliding. That scene is real and it is the wrong
one to lead with: it is precisely the case a single harness can solve inside
itself, and vendors are actively doing so. Session management landed in Codex
Desktop and changed one practitioner's whole flow.

The case that survives is the one people already run: **one vendor's agent
implements, another's reviews, both against one repository, neither aware of the
other.** No model vendor will build the coordination layer that makes a
competitor a first-class peer. That is structural, not an oversight, and it is
the only ground a separate tool has.

**Rules that survive every edit.** Do not describe Tasq as an agent runtime, a
managed cloud service, or proof that actor-provided evidence is true. Do not
imply that Local coordinates separate machines. Keep "public alpha" visible
whenever the post mentions availability. Never claim adoption that does not
exist: there are no users yet, so there are no testimonials, and the only case
study that may be cited is this project's own dogfooding. No em-dashes.

## LinkedIn

Most of the interesting multi-agent setups I see now cross vendors. One tool
implements, another reviews, and both work against the same repository and the
same backlog.

The coordination usually rests on an issue tracker's status field, and that
field is a label. Nothing stops two agents picking up the same issue, and
nothing tells you when one of them died holding it.

Tasq is a ledger they share, where the unit is a claim rather than a ticket. An
agent takes an exclusive lease on a piece of work and the others are refused by
name. The lease expires, so an agent that dies frees its work without anyone
cleaning up, and `tasq fleet` answers who is holding what right now.

Two things I have not found elsewhere. It can require an inspectable receipt
before work is closed, because an agent reporting success is an assertion rather
than evidence. And it records what it refused, so "how many collisions did this
prevent last week" is a number rather than a feeling.

Local-first, one SQLite file you own, Apache-2.0, reachable over MCP or a plain
shell. It is a public alpha and it is honest about that.

https://tasq.run

## Show HN

### Title

Show HN: Tasq - a claim ledger your coding agents share, across vendors

### Body

I run coding agents from more than one vendor against the same repository. One
implements, another reviews. The coordination rested on an issue tracker's
status field, and that turned out to be the whole problem: a status is a label,
so nothing prevents two agents taking the same work, and nothing notices when
one of them dies holding it.

Tasq is a local-first ledger they share. The unit is a claim, not a ticket.

**A claim is an exclusive lease that expires.** One agent takes the work and the
others are refused, by name, so a refused agent can wait or pick something else
instead of guessing. If the holder dies, the lease lapses and the work returns.
That is also why you can see your fleet without a daemon watching processes: the
question is whether anyone still owns the work, not whether a PID exists.

**It records what it refused.** This is the part I wanted and could not find
anywhere. A tracker keeps a complete account of everything it allowed and no
trace of anything it prevented, so "did this help" stays a feeling. `tasq
contention` counts the standoffs, and counts a polling agent turned away four
hundred times as one situation rather than four hundred rows.

**A succeeded attempt is not a completed commitment.** They are different facts
and Tasq stores them separately. A commitment can require an inspectable receipt
before it closes.

**Both doors are real.** Agents reach it over MCP or by running the CLI, which
is what a shell-capable agent already knows how to do. Two differently
identified clients coordinating on one ledger is a test that runs in CI.

It is one SQLite file you own, Apache-2.0, no service to sign up for.

Honest about the state. Public alpha, and there are no users yet, so nothing
here is a case study except my own use while building it. Local coordinates
agents sharing one ledger on one machine; a self-hosted server exists for
remote, and managed cloud does not. The store format moved in this release, so
an existing ledger migrates forward once and `tasq store upgrade` makes that an
explicit decision rather than a side effect.

Try it without installing anything:

    npx @tasq-run/cli@0.6.0 demo

The demo runs two agents against one task in a throwaway home and shows you
three refusals in a row: the second claim, the close by a non-holder, and the
close without a receipt. That is the whole product in about fifteen seconds, and
it does not read or change anything you already have.

https://tasq.run  ·  https://github.com/gwendall/tasq

## What to watch, and what would end it

The point of publishing is not signups, it is the answer to one question:
**do collisions actually happen to other people.**

ADR-025 fixes what would end this. The short form: twenty days of real
multi-agent work producing fewer than five standoffs in `tasq contention`, or
five practitioners who have never been bitten by a collision or by an agent that
died unnoticed, and the honest move is to stop rather than to build more.

Anyone replying "my harness already handles that" is answering the question, not
missing the point. Record it.
